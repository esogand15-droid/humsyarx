# 🏗 طراحی رفع باگ «کلون ⭐ با کلیک» — فاز ۳

> گزینه‌ی انتخابی (پیشنهاد کاربر): **Copy-on-Write در لحظه‌ی ذخیره + سایه‌اندازی + هویت پایدار (logical_id مشتق از fork_of) + ↩️ بازگشت به سراسری.** گزینه‌های «ویرایش in-place با فیلد محدوده» (ریسک از دست رفتن تاریخچه/هم‌زمانی) و «field-overlay» (بازطراحی سنگین qbank/resources) رد شدند — جزئیات در جلسه.

## ۱. اصول ثابت رفتاری

1. **هیچ ساخت داده‌ای با مشاهده/بازکردن/پیمایش اتفاق نمی‌افتد** — فقط با «ذخیره‌ی تغییر» یا «دستور صریح ادمین ارشد».
2. **یک تابع واحد نمای مؤثر:** `db.bs_get_sessions_effective` (و قرینه‌ی ref) تنها مرجع سایه‌اندازی؛ همه‌ی لایه‌ها مصرف‌کننده‌اند (حذف پیاده‌سازی تکراری web_admin).
3. **دسترسی فقط سمت سرور:** intake هدف همیشه از scope سروری استخراج می‌شود؛ پارامتر کلاینت هرگز تعیین‌کننده‌ی محدوده نیست.
4. **بدون حذف داده:** unfork = حذف fork (خواست کاربر)، حذف base دارای fork = مسدود در همه‌ی لایه‌ها (هم‌تراز با ربات/API فعلی؛ cascade وب حذف می‌شود).
5. **نشانگر یکدست در ابتدای دکمه:** `🌐 سراسری` · `⭐ شخصی‌سازی‌شده (ورودی X)` · `📅 بومی ورودی` · `↩️ بازگشت به سراسری` — دانشجو هیچ نشانگری نمی‌بیند.
6. **سربرگ محدوده** روی همه‌ی صفحه‌های مدیریتی: `📍 محدوده: سراسری (همه ورودی‌ها)` / `📍 محدوده: {ورودی} — تغییرات پیش‌فرض فقط همین ورودی`.

## ۲. مدل داده (تغییر حداقلی، بدون backfill اجباری)

- بدون فیلد جدید روی base. **هویت پایدار = `logical_id` مشتق‌شده**: `logical_id(s) = s.fork_of or s._id` — base مالک هویت؛ fork همان هویت منطقی را با خود دارد (برای cache/پیشرفت دانشجو در پاسخ‌های API هم exposición می‌شود).
- **ایندکس یکتای جزئی** روی `bs_sessions` و `ref_books`: `{fork_of: 1, intake: 1}` با `partialFilterExpression: {fork_of: {$type: 'string'}, intake: {$type: 'string'}}` — فقط روی forkها یکتایی می‌دهد؛ baseها (بدون fork_of) اثر نمی‌گیرند. با try/except: اگر کلون تکراری موجود باشد، ثبت می‌شود و **migration** پیش از ساخت ایندکس رفعش می‌کند.
- **ساخت اتمیک override:** `bs_ensure_override(session_id, intake)`:
  1. fast-path: fork موجود → برگردان (created=False)
  2. `find_one_and_update({'fork_of','intake'}, {'$setOnInsert': {...}}, upsert=True, return_document=AFTER)` — در race فقط یک برنده
  3. کپی فایل‌ها فقط اگر `bs_content.count(session_id)==0` (ایدمپوتنت؛ فایل‌ها همان‌طور ارجاع file_id دارند، notif_sent=True، downloads=0، fork_of فایل پایتی می‌شود)
  - `bs_fork_session` قدیمی به این تابع منتقل می‌شود (اسم قدیمی به‌عنوان alias می‌ماند برای سازگاری).
- **واگرایی از سراسری (R5):** هنگام بازکردن fork، اگر base فایل‌هایی دارد که fork ندارد، نوار اطلاع «🌐 نسخه‌ی سراسری N فایل جدیدتر دارد» + دکمه «📥 افزودن فایل‌های جدید از سراسری» (فقط افزودنی؛ هیچ فایلی را بازنویسی/حذف نمی‌کند). ادغام کامل‌تر = «نیازمند تصمیم».

## ۳. ماتریس رفتار مطلوب (نقش × رکورد × عمل)

| رکورد | کاربر/حالت | بازکردن | اولین ذخیره‌ی تغییر | ↩️ |
|---|---|---|---|---|
| جلسه سراسری | ادمین ورودی X (scoped) | نمایه، بدون ساخت | **CoW خودکار**: fork برای X + اطلاع یک‌باره + ثبت تغییر روی fork | — |
| جلسه سراسری | ارشد، محدوده ورودی X | نمایه + دو گزینه در ورود به ویرایش: «🌐 ویرایش سراسری (همه)» / «⭐ فقط ورودی X» (پیش‌فرض: X) | انتخاب‌شده اجرا می‌شود؛ ⭐ یعنی CoW | — |
| جلسه سراسری | ارشد، محدوده سراسری | نمایه + هشدار سربرگ «ویرایش = همه‌ی ورودی‌ها» | ویرایش in-place سراسری | — |
| جلسه fork (⭐) | scoped X / ارشد در X | نمایه fork | ویرایش روی fork | ✓ حذف fork، بازگشت به سراسری |
| جلسه بومی (📅) | scoped خودش / ارشد | نمایه | ویرایش in-place | — |
| جلسه ورودی دیگر | scoped غیر X | — | 🛡 مسدود (403/«دسترسی ندارید») | — |
| درس | هر دو | — | intake درس فقط ارشد/سراسری تغییرپذیر؛ درس fork ندارد | — |
| کتاب رفرنس | همان قواعد جلسه | همان | همان (ref_fork_book → ensure_override قرینه) | ✓ |

**حذف:** base دارای fork در هر ۴ لایه مسدود با پیام فهرست ورودی‌های دارای override (وب cascade حذف شد — web_admin.py:4305). unfork/حذف fork مجاز است (حذف override، نه محتوای سراسری).

## ۴. تغییرات لایه‌به‌لایه

### ۴.۱ DAL (db/content.py + db/core.py)
- `bs_ensure_override` / `ref_ensure_override` اتمیک (§۲)؛ `bs_fork_session`/`ref_fork_book` = alias.
- `bs_override_counts(lesson_id)` → `{base_id: n}` برای نشان `⭐n` در نمای سراسری.
- نمای سراسریِ منطقی: `bs_get_sessions(lesson)` خام + در لایه‌ی UI: fork پنهان زیر base (R2)؛ یتیم‌ها (base حذف‌شده) نمایش داده شوند.
- شمارش‌های منطقی: `bs_sessions.count_documents({lesson_id, fork_of {$exists: false}})` + یتیم‌ها (R6)؛ stats داشبورد و data-quality فایل‌ها هم fork را در شمارش سراسری حذف می‌کنند (`fork_of` exists → skip) — نمای ورودی هم «مؤثر» می‌شمارد.
- ایندکس یکتای جزئی (§۲) در `db/core.py` با fallback لاگ‌خط.

### ۴.۲ ربات (content_admin.py + basic_science.py)
- **حذف دکمه‌ی ✂️ از ردیف جلسات و از `_specialize_row`** — شخصی‌سازی دیگر اکشن مستقل نیست؛ در نقطه‌ی ذخیره CoW می‌شود (R1).
- `_show_sessions`:
  - سربرگ محدوده + legend یکدست (§۱-۵، R7).
  - سطل سراسری (ارشد، ctx=''): **جمع‌کردن forkها زیر base** — یک ردیف با نشان `⭐n` (n=تعداد ورودی‌های دارای override)؛ شمارنده «N جلسه» منطقی (R2).
  - سطل ورودی: effective (موجود) + نشان‌ها در ابتدای متن؛ ↩️ با برچسب «↩️ بازگشت به سراسری».
- جریان ویرایش (✏️ prompt→save، 📤 آپلود، 🗑 حذف فایل، ترتیب): همه از `_writable_session(sid, actor)` می‌گذرند:
  - رکورد بومی/fork در scope → همان sid
  - رکورد سراسری + scoped → `bs_ensure_override` (اطلاع یک‌باره «⭐ برای ورودی X شخصی‌سازی شد»)
  - رکورد سراسری + ارشدِ در ctx ورودی → **صفحه‌ی انتخاب**: `🌐 ویرایش سراسری (همه ورودی‌ها)` / `⭐ فقط ورودی {ctx}` → مسیر انتخابی
  - رکورد سراسری + ارشدِ سراسری → in-place + سربرگ هشدار
  - callback_data ساختار قبلی (≤64B) حفظ می‌شود؛ فقط کاربرد ✂️ حذف و ↩️ برچسب می‌گیرد. callbacks قدیمیِ ✂️ برای سازگاری به ensure_override هدایت می‌شوند (نه خطا).
- دانشجو (basic_science.py): حذف ⭐ از متن دکمه (R7) — نمای مؤثر بدون تغییر.
- `_h_fork_session` → به ensure_override هدایت + پیام درست («⭐ نسخه‌ی اختصاصی ورودی X آماده شد» — دیگر هیچ دکمه‌ی مستقیمی آن را صدا نمی‌زند؛ فقط callbackهای قدیمی).

### ۴.۳ API (api/routers/content_admin.py + resources.py + web_admin.py)
- endpointهای **فوری-fork** (`POST .../fork`) باقی می‌مانند (سازگاری) ولی به ensure_override اتمیک منتقل می‌شوند؛ در مستندات «صریح/ارشد» علامت می‌خورند.
- endpointهای تغییر: `PATCH /sessions/{sid}`، آپلود/حذف محتوا، reorder، edit درس: پارامتر اختیاری `edit_scope ∈ {'auto','global','intake'}` (پیش‌فرض `auto`):
  - `auto` + scoped → CoW برای scope خودش
  - `auto` + ارشد → in-place (رفتار فعلی) — پنل هنگام انتخاب ورودی `intake` می‌فرستد
  - `global` → فقط ارشد؛ در غیر این صورت 403
  - `intake` → CoW برای intake انتخابی (سرور چک: ارشدِ همان ورودی یا scoped خودش)
  - پاسخ همیشه `logical_id` + `override_created` دارد.
- `resources.py`: شمارش فایل با `count_documents({'session_id'})` جایگزین full-scan (R6-کارایی)؛ پاسخ‌ها `logical_id` می‌گیرند.
- `web_admin.py`: `/content/tree` → مصرف `bs_get_sessions_effective` (حذف کپی محلی) + نشان `⭐n`؛ حذف base دارای fork → **409** به‌جای cascade (R7)؛ reorder فقط base/بومی.

### ۴.۴ پنل وب (webadmin/src/pages/Content.jsx)

- SessionInspector: ویرایش جلسه‌ی سراسری در حالتِ انتخاب ورودی → دیالوگ انتخاب «🌐 ویرایش سراسری / ⭐ فقط {ورودی}» → `edit_scope` ارسال؛ حذف دارای override → پیام مسدودی با فهرست ورودی‌ها.
- نشان‌ها: 🌐/⭐(ورودی)/📅 در ابتدای عنوان + legend یکسان با ربات؛ ↩️ با برچسب (API موجود caUnforkSession).

### ۴.۵ مینی‌اپ ادمین (miniapp/src/pages/Admin/ContentLibrary.jsx)

### ۴.۶ Migration (`tools/migration/content_forks.py` — جدید)
`--dry-run` (پیش‌فرض) / `--apply` / `--backup-dir` (پیش‌فرض `backups/`) / idempotent:
1. پشتیبان JSON کامل مجموعه‌های درگیر.
2. رده‌بندی forkهای جلسه/کتاب:
   - **A** (بدون تغییر واقعی: فیلدهای عنوان/شماره/معلم یکی + همان مجموعه فایل) → `archived: true` + گزارش (فقط در dry-run فهرست)
   - **B** (تغییر واقعی) → حفظ (بدون تغییر)
   - **C** (تکراری: چند fork برای یک (fork_of,intake)) → نگه‌داشتن غنی‌ترین/جدیدترین، بقیه `archived: true`
   - **D** (یتیم: base حذف‌شده) → قطع پیوند: `fork_of` حذف + intake همان → «بومی ورودی»
3. ساخت ایندکس‌های یکتای جزئی (بعد از رفع C).
4. rollback: `tools/migration/content_forks_rollback.py` — بازگردانی از backup با upsert بر اساس _id.

## ۵. ریسک‌ها و تصمیم‌های «حدس/نیازمند تصمیم»

- **حدس:** فیلدهای بولدی که کلون‌های قدیمی دارند معادل «تغییر واقعی» نیستند (فقط fork_of داشتن فایل کافی نیست؛ مقایسه‌ی محتوایی انجام می‌شود). ریسک: forkهایی که فقط «ترتیب» عوض شده‌اند → B در نظر گرفته می‌شوند (محافظه‌کارانه، بدون حذف).
- **حدس:** `logical_id` مشتق از fork_of (بدون فیلد فیزیکی جدید) — اگر روزی base حذف شود fork یتیم می‌شود؛ گارد حذف این حالت را می‌بندد.
- **نیازمند تصمیم:** ادغام دوطرفه‌ی تغییرات سراسری↔fork (الان فقط افزودنی)؛ اعلان ادمین ورودی وقتی سراسری فایل جدید می‌گیرد؛ انتقال تاریخچه‌ی دانلود base به fork.
- **حدس:** stats داشبورد سراسری = شمارش منطقی (بدون fork)؛ شمارش ورودی = مؤثر.
