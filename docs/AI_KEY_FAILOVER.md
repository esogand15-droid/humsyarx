# 🔑 فال‌بک چند-کلیدی هوشیار (Key Failover) — ماموریت ۷

> هر ارائه‌دهنده (Gemini و …) می‌تواند **به تعداد دلخواه کلید API** داشته باشد. وقتی یکی
> سهمیه/لیمیت خورد (429) یا خطا داد، **همان درخواست بی‌درنگ با کلید بعدیِ سالم** ادامه
> می‌یابد — و اگر آن هم لیمیت خورد، کلید بعدی؛ تا آخرین کلید.

## ۱. مدل داده

- Vault در تنظیمات `ai_api_keys` (رمزنگاری‌شده در صورت فعال‌بودن FERNET_KEY):
  `{provider: [key1, key2, ...]}` — **به‌ترتیبِ اولویت**.
- فرم قدیمی `{provider: "key"}` خودکار به `[key]` نرمال می‌شود (بدون migration).
- `get_ai_config()` علاوه بر فیلدهای قدیمی (`api_key` = کلید اول، `vault`/`api_keys` = رشته برای سازگاری)،
  فیلدهای جدید می‌دهد: `api_key_list`، `image_api_key_list`، `vault_multi`، `vault_counts`.
- آینه‌های legacy (`ai_api_key_{pid}` و `ai_api_key`) فقط کلیدِ اول را نگه می‌دارند.

## ۲. رفتار فال‌بک (runtime)

- **چرخش روی کدام خطاها؟**
  - `AIQuotaError` (429/سهمیه) → cooldown **۱۲۰ ثانیه**
  - `AIConfigError` (400/401/403/404 — کلید نامعتبر) → cooldown **۱ ساعت**
  - 5xx/شبکه/timeout و کدهای تصویرِ سهمیه/کلید/سرویس → cooldown **۳۰ ثانیه**
  - خطاهای منطقی (مثل بلاکِ ایمنی، JSON خراب) → **چرخش نمی‌کنند** (با هر کلیدی همین می‌شود).
- وضعیت کلیدها فقط **در حافظه‌ی پروسه** (`_KEY_STATE`)؛ ری‌استارت = شروعِ تمیز.
- `ordered_keys`: کلیدهای cooldownشده بدون هیچ درخواست شبکه‌ای رد می‌شوند؛ اگر
  *همه* در cooldown باشند، به‌ترتیبِ نزدیک‌ترینِ انقضا امتحان می‌شوند (هرگز بدونِ تلاش، خطا نمی‌دهیم).
- **استریم:** تعویض کلید فقط تا وقتی هیچ پاسخی به کاربر جاری **نشده** ممکن است؛
  پس از شروعِ جاری‌شدنِ جواب، خطا همان‌جا بالا می‌رود (پاسخِ نیمه‌جاری برگشت ندارد).
- کلیدِ آخر اگر شکست بخورد، خطای اصلی/کاربرپسند همان کلید عیناً برمی‌گردد.

## ۳. مسیرهای پوشش‌داده‌شده

| مسیر | فال‌بک |
|---|---|
| چت هوشیار (ربات + API + مینی‌اپ) — `ask_ai_stream` | ✅ |
| اطلاعیه‌ی AI / پیش‌نویس پاسخ تیکت / طرح سوال / JSON ساخت‌یافته | ✅ |
| ساخت تصویر (`generate_image` در API) | ✅ |
| آپلود PDF مرجع (ربات + API) | ✅ |
| فهرست زنده‌ی مدل‌ها (`list_provider_models`) | ✅ |
| دکمه‌ی «تست اتصال» (از مسیر ask_ai) | ✅ خودکار |

## ۴. مدیریت کلیدها

**پنل وب (تنظیمات هوشیار → «🔑 کلیدهای فال‌بک»):** فهرست ماسک‌شده با وضعیت (🟢 سالم /
🟡 استراحت / 🔴 شکست‌خورده + آخرین خطا)، افزودن، حذف تک‌تک، «🧪 تست همه».
(افزودن/حذف فقط مالک؛ کلید هرگز به مرورگر برنمی‌گردد.)

**API (owner/ai.manage):**
- `GET  /api/web-admin/ai/keys/{provider}` — فهرست ماسک‌شده + وضعیت
- `POST /api/web-admin/ai/keys/{provider}` — افزودن `{api_key}`
- `DELETE /api/web-admin/ai/keys/{provider}/{index}` — حذف (۱-مبنا)
- `POST /api/web-admin/ai/keys/{provider}/test` — تست همه per-key
- همان‌ها روی روتر مدیریتی: `/vault/{provider}/keys…`
- `PUT /vault/{provider}` (قدیمی) = جایگزینیِ همه‌ی کلیدها با یک کلید — بدون تغییر.

**ربات (مدیریت هوشیار → 🗝️ Vault):** هر provider با تعداد کلید + وضعیت؛ «➕ افزودن کلید
فال‌بک» (حفظ قبلی‌ها) و «جایگزینی همه» و حذف تک‌تک.

## ۵. محدودیت‌ها/تصمیم‌ها

- حداکثر **۲۰ کلید** برای هر provider.
- «چرخش کلید» قدیمی پنل = جایگزینی (فقط مالک) — دست‌نخورده؛ افزودنِ بدونِ حذف از KeysPanel.
- وضعیت cooldown در حافظه است؛ بین چند process (ربات/API جدا) به‌اشتراک گذاشته نمی‌شود —
  هر پروسه مستقل فال‌بک می‌گیرد (رفتار امن و درست، فقط «استراحتِ» یک کلید بین پروسه‌ها همگام نیست).
- ترتیب = اولویت ثابت (اول همیشه کلید ۱ امتحان می‌شود مگر cooldown باشد)؛ round-robin عمداً نیست.

## ۶. تست‌ها
